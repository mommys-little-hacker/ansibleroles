# AGENTS.md — инструкции для ИИ-агентов

Приватный репозиторий Ansible-ролей проекта `qwertys.ru`. Работая в нём,
придерживайся правил ниже.

## Суть проекта

- Монорепозиторий с Ansible-ролями: каждая роль — каталог в `roles/`,
  имя каталога = имя роли.
- Репозиторий **закрытый**: код и инструкции по доступу нельзя публиковать,
  открывать наружу или выносить в публичные места. Все примеры в доках —
  только с приватным SSH-URL (`git@<git-сервер>:<группа>/...`).
- Репозиторий не привязан к конкретной git-платформе: не вводить зависимости
  от GitHub (Actions, `gh` CLI и т.п.) без явного запроса пользователя.
- Потребители подключают репозиторий целиком (submodule/clone) через
  `roles_path` — см. README.md. Не менять механизм подключения без обсуждения.

## Структура

- `roles/<имя>/` — роли. Канонический скелет: `defaults/`, `tasks/`,
  `handlers/`, `files/`, `templates/`, `meta/`, `vars/`, опционально `molecule/`.
- `playbooks/` — примеры плейбуков.
- `requirements.yml` — внешние коллекции Galaxy.
- `scripts/lint.sh` — локальный прогон линтеров (yamllint + ansible-lint);
  должен проходить без ошибок. CI, если настроен на git-платформе, — тоже.

## Правила написания ролей

1. **Переменные**
   - Всё конфигурируемое — в `defaults/main.yml` с префиксом имени роли:
     `common_packages`, `nginx_conf_dir`.
   - `vars/main.yml` — только внутренние вычисляемые значения.
   - Булевы переменные — со смысловыми именами и значениями `true/false`.
2. **Модули** — только с FQCN: `ansible.builtin.package`,
   `ansible.builtin.template`, `community.general.*` и т.д. Новые
   внешние коллекции добавляй в `requirements.yml`.
3. **Идемпотентность** — повторный запуск роли не должен менять состояние.
   Используй `changed_when`/`creates` для shell/command.
4. **Секреты** — запрещены в репозитории в открытом виде. Только
   `ansible-vault` (пароль vault — вне репозитория). Не коммить токены,
   ключи, пароли, даже «тестовые».
5. **Стиль YAML** — 2 пробела, `---` в начале файла, строки ≤ 120 символов
   (см. `.yamllint`).
6. **Имена ролей** — строчные буквы, цифры, подчёркивания; конкретные, не
   «типовые» (`backup_client`, а не `utils`).
7. Документация (README ролей, таблицы в корневом README) — на русском,
   идентификаторы в коде — на английском.

## Обязательные проверки перед коммитом

Инструменты живут в виртуальном окружении `.ansibleroles/` в корне
репозитория. Если его нет — создай по инструкции из README
(раздел «Требования»).

```bash
source .ansibleroles/bin/activate   # или используй .ansibleroles/bin/<tool>
yamllint .
ansible-lint
```

То же одной командой: `./scripts/lint.sh`.

Обе команды должны проходить без ошибок (warnings из `warn_list`
обсуждаются, но не игнорируются молча). Если в роли есть
`molecule/` — прогоняй `molecule test` для затронутых ролей.

## Коммиты и git

- Осмысленные сообщения в стиле imperative: `Add backup_client role`.
- Не делать force-push, не переписывать историю чужих веток, не удалять теги.
- Новая роль / новая функциональность — через merge/pull request в основную
  ветку `main`; линтеры (`./scripts/lint.sh`) и CI, если настроен, должны пройти.
- При добавлении роли: дополнить таблицу ролей в README.md и создать
  README самой роли (назначение, переменные с дефолтами, пример использования).

## Что делать осторожно

- Не изменять `ansible.cfg`, конфиги линтеров, `scripts/lint.sh` и CI без
  необходимости — они согласованы.
- Не удалять файлы, которых не создавал сам в этой сессии, без явного
  запроса пользователя.
- Не выполнять playbook'и против реальных хостов без явной команды
  пользователя; проверка — только `--check --diff` или локально.
- Если задача неоднозначна (имя роли, набор переменных, breaking change) —
  спросить пользователя, а не догадываться.
